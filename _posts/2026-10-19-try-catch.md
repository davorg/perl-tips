When processing several configuration values, one invalid entry should not necessarily abort the whole batch. You need a clear boundary around validation, a useful failure message, and a way to continue with later entries without running success-only work after a failure. Perl's `try` and `catch` syntax provides that boundary. This standalone example validates candidate TCP port numbers, reports rejected values, and counts only successful results.

```perl
use v5.44;
use strict;
use warnings;
use feature 'try';

sub parse_port ($text) {
    die "expected decimal digits\n"
        unless $text =~ /\A[0-9]{1,5}\z/;

    my $port = 0 + $text;
    die "port must be between 1 and 65535\n"
        unless $port >= 1 && $port <= 65535;

    return $port;
}

my @candidates = ('8080', '0', 'eight', '443');
my $accepted = 0;

for my $text (@candidates) {
    try {
        my $port = parse_port($text);
        say "Accepted port: $port";
        ++$accepted;
    }
    catch ($error) {
        chomp $error;
        say "Rejected '$text': $error";
    }
}

say "Accepted total: $accepted";

```

Expected output:

```text
Accepted port: 8080
Rejected '0': port must be between 1 and 65535
Rejected 'eight': expected decimal digits
Accepted port: 443
Accepted total: 2

```

The program enables the stable syntax with `use feature 'try';`. The feature was introduced in Perl 5.34 and became stable in Perl 5.40; this example targets Perl 5.44. Strict checking and warnings remain enabled.

The `parse_port` subroutine first requires one to five ASCII decimal digits, then converts the text to a number and checks the permitted range. Checking the text before numeric conversion avoids warnings for nonnumeric input. Leading zeros are accepted, but whitespace, signs, and more than five digits are rejected deliberately.

Each loop iteration places parsing and its success-only actions inside `try`. If validation calls `die`, execution skips the remaining statements in that block and enters `catch`. Consequently, rejected entries never increment `$accepted`, while the next iteration still runs. The final count shows that both valid entries were processed despite the failures between them.

Write the handler as `catch ($error)`, not `catch (my $error)`. The handler receives the exception in a lexical variable whose scope is the handler block. Here, each exception is a controlled string ending in a newline, so `die` does not append a source location. The handler uses `chomp` before printing its own complete diagnostic line.

Keep recovery boundaries deliberate: this handler treats every exception from its protected block as a rejected candidate. In production, avoid silently swallowing unexpected failures. Also, `catch` handles exceptions, not ordinary warnings or unsuccessful return values unless your code turns those conditions into exceptions.

Example tested with Perl 5.44.
